# 证明修复、穷举器纠错与效率检查

## 已修改并验证的行为

### 源码不变的证明修复

比较完整 SolverOutput 的非源码字段。步骤、证明、复杂度或映射发生变化时，保存本轮 solution.json 和独立 reasoning_revision_id，仍执行新的逐步骤评审。代码 revision_id 与源码哈希不变，复用当前最佳版本的编译和判题记录。只有源码和全部推理材料都相同时，才走“没有修改”的分支。

证明通过后更新最佳解法及证明引用；失败的证明仍保存在修复历史。检查点保存新证明和复用的判题证据，恢复时不会再次求解/编译/判题。报告选取最佳评审时同时匹配代码版本和证明版本，防止错误展示初始旧证明。

增加 repair_attempt_count、proof_only_round_count、code_revision_count，避免将证明修订与代码版本数量混为一谈。WebUI 对证明修复显示“重新评审证明”，说明判题结果复用。

### 穷举器的有界纠错

最多 3 个程序候选，每个候选独立保存生成代码、编译结果、公开样例结果和小规模运行结果。文件 I/O/基本源代码检查、编译或公开样例失败时，向模型反馈失败类别、编译诊断或公开反例，以及上一份代码，要求返回完整修正版。

新的候选不得复用被拒绝候选的输出作为正确答案。只有编译、公开样例和小规模运行全部有效后，才对候选解法执行差分比较。模型网络/JSON 重试已由模型客户端处理，耗尽后不再套另一层重复请求；基础设施不可用也不会通过重复生成代码来掩盖。

每次阶段结果持久化，重启复用已完成工作；3 个候选均失败后明确降级，后续修复轮不会重新开启无限纠错。仍不将模型生成的穷举器当作形式化证明。

本次不新增付费模型调用，不改写两次历史真实评测。测试覆盖证明修复及恢复、旧报告与新证明匹配、残缺代码→纠错成功、编译错误→纠错成功、样例错误→纠错成功、候选缓存隔离、三轮失败降级。

292 项 Python 测试和 28 项前端测试通过。另在真实 Docker 中用历史 68 字符残缺代码作为第一候选、确定的完整顶点覆盖穷举程序作为第二候选，验证了无效程序反馈、样例校验及 6 个小规模输入对拍；结果 PASSED、程序候选数 2、付费模型调用数 0。该测试验证纠错执行链路，不代表真实 Hy3 每次都能生成正确穷举器。

## 只读效率检查：未实施的建议

历史难题 run_Uqj8Z6xbzUlhxkkF 的四次正式判题约为 50.0、29.9、30.2、29.9 秒，合计约 140 秒；模型修复请求累计约 1167 秒，代码复核请求累计约 1153 秒。后两项包含失败尝试，且不同角色可能并行，不能简单相加当作总墙钟时间。

建议按以下优先级考虑，不改变现有模型、high 推理强度、证据要求、私有测试覆盖或修复策略：

1. **先补齐分段耗时观测。** 记录请求开始、响应头、首个内容事件、正文开始、完整结束的时间。当前 first_event_ms 从创建流解析器开始计时，不包含连接和响应头等待，不能用于判断完整首响应延迟。增加只读观测可帮助区分服务端推理、排队和链路断连，避免盲目缩短超时或减少推理。
2. **减少流式接收期间的数据库查询。** 当前每个 SSE 行都会检查取消，回调进入 Store.get_run。难题各角色累计有数万事件，对应大量重复 SQLite 查询。可以维护运行级取消信号，数据库仅用于跨进程同步；保留一个较短的同步周期并验证取消响应上限。这有潜在收益，但没有基准测试前不能宣称其是主要瓶颈，也不能直接删除取消检查。
3. **缓存健康检查与编译产物定位。** Docker 版本/镜像检查和遍历 runs 目录定位编译元数据可以短期缓存或使用索引；每次实际执行仍验证二进制哈希、所属题目和资源约束。收益属于固定开销，预计小于模型生成耗时，需测量后判断是否值得实施。
4. **复用 HTTP 连接并先排查断流。** 在相同配置的客户端生命周期内复用连接池，保持相同请求内容、鉴权、超时和关闭规则，可能减少重复连接开销；但本次 RemoteProtocolError 的具体上游原因尚未证实，连接池并不保证解决它。
5. **只压缩重复元数据，不删题意或证据。** 题面、视觉补充及诊断在提示中可能重复携带。可以先统计重复字节，将相同元数据规范化；真实题目条件、完整代码、步骤证据和反例应保留，并用回放检查信息等价性。未证明等价前不建议删减。

不建议为了提速降低 high、放宽评审校验、省略测试点、把不完整响应当作成功、减少必要的正确性验证，或直接取消异常复核。这些可能影响解题能力或可信度，超出本次只读效率检查范围。
