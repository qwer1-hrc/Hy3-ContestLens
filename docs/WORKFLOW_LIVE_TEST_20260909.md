## 已验证的机制

1. 简单/困难题的难度路由符合“省选/NOI−及以上”的门槛。
2. 严格逐步骤证据要求在真实 Hy3 返回中生效，实际执行的评审没有空 assessments。
3. 难题公开样例失败会暂缓昂贵评审，并将公开输入、预期和实际输出用于修复。
4. 错误分类在 r001 后正确转为 WA 优先，没有继续沿用初始 TLE 的优化方向。本次没有真实 RE/MLE，不能把这些分支算作本次实测覆盖。
5. 第三轮请求确实携带 r002 的失败修改。用实际最佳版本、诊断、公开反例、失败记忆和 schema 重建请求后，messages_sha256 与真实第三轮日志一致。
6. 概率建模重检在简单题真实触发，未突破 3 次修复调用预算；但触发来自证明变化未被识别，应先修复该问题。

## 优先修复项

1. 支持只修改证明/步骤的候选：即使 C++ 不变，也保存新推理版本，重新做过程评审，复用已有编译和判题结果。不能直接当作无改进而丢弃。
2. 穷举器生成要增加程序完整性/文件 I/O/编译与样例验收后的有界纠错重试。当前只校验 JSON，遇到不完整程序即永久降级，真实小规模穷举路径未跑通。
3. 报告分别统计模型修复尝试、代码修订与证明修订，避免把三次修复调用显示成一轮。

结论：严格评审、公开样例反馈、失败记忆与有界重检的主链路可运行；难题从 0 分提高到 84 分，但尚不能把整个增强流程视为验收通过，尤其是证明单独修复与穷举器自动纠错。
